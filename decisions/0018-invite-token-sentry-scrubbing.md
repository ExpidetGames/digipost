# Invitation token in the URL: Sentry scrubbing, residual access-log risk

Document type: decision
Lifecycle: active
Owner: src/platform/observability
Scope: How the application-level observability layer (Sentry) handles the invitation
token that decisions/0014-workspaces-and-access.md put in the URL path
(`/invite/<token>`), and what risk that decision does not remove
Canonical responsibility: Active source for why `src/platform/observability`'s
`sentryInitOptions` redacts `/invite/<token>` from event/breadcrumb URLs, and for the
residual risk (hosting/CDN/proxy access logs) that redaction does not close
Maintenance triggers:
- The invitation URL shape changes (a different path, a token moved to a query string
  or a header)
- Sentry's `beforeSend`/`beforeBreadcrumb` API changes shape
- A hosting/CDN/proxy access-log retention or redaction policy is adopted for this
  project
Last verified: 2026-09-20, P6 review (finding B3)

## Status
Accepted

## Context

decisions/0014-workspaces-and-access.md put the invitation's token in the URL path itself
(`/invite/<token>`, a hashed-at-rest, single-use, 7-day-expiry token) rather than in a
request body or header, because it has to be clickable from a plain e-mail link. A URL
path segment is, by construction, visible to every layer that ever sees the request line:
the browser's own history, any intermediate proxy, and - the concern this ADR addresses -
this application's own error/performance monitoring (`src/platform/observability`, Sentry).
Sentry's default instrumentation captures the current URL on `request.url` for server
events and as `url`/`to`/`from` breadcrumb data for client-side navigation and HTTP
breadcrumbs; without any redaction, opening `/invite/<token>` (whether or not anything
actually errors on that page) would put the plaintext token into Sentry, a third-party
sub-processor, and into Sentry's own retention and any teammate with Sentry project access.

## Decision

1. **Redact, do not avoid.** `src/platform/observability/core/init-options.ts`'s
   `sentryInitOptions` now also returns `beforeSend`/`beforeBreadcrumb` hooks (previously it
   returned only `dsn`/`sendDefaultPii`/`tracesSampleRate`), shared by all three Sentry
   config files (`src/sentry.server.config.ts`, `src/sentry.edge.config.ts`,
   `src/instrumentation-client.ts`) exactly the way `dsn`/`sendDefaultPii`/`tracesSampleRate`
   already were - one change here reaches every runtime. `redactInviteTokenFromUrl` replaces
   any `/invite/<token>` path segment (matched structurally: `/invite/` followed by anything
   up to the next `/`, `?`, or `#`) with `/invite/[redacted]` in `event.request.url`, every
   `event.breadcrumbs[].data.{url,to,from}` string, and `breadcrumb.message`. This is a
   redaction of the token, not a redesign of the invitation flow itself - `/invite/<token>`
   still exists and still works exactly as decisions/0014 describes; only what reaches
   Sentry changes.
2. **Structural match, not a token-specific allowlist.** The redaction targets the URL
   *shape* (`/invite/<anything>`), not a specific token value, so it also covers an already
   -expired, already-used, or entirely invalid token in the path (all of which still reach
   this same page and could still generate a Sentry event, e.g. a rendering error unrelated
   to the token's validity).
3. **`core/init-options.ts` stays SDK-import-free.** The redaction functions operate on a
   minimal structural type (`{ request?: { url }, breadcrumbs?: [...] }`), not `@sentry/nextjs`'s
   own `Event`/`Breadcrumb` types, preserving this file's existing "pure, no SDK import"
   property (its own header comment) so it stays trivially unit-testable without mocking the
   SDK.

## Consequences

- Positive: no Sentry event or breadcrumb generated by this application ever carries a
  plaintext invitation token, regardless of which runtime (server, edge, browser) generated
  it, without any per-call-site opt-in - the redaction is unconditional inside the one
  shared `sentryInitOptions`.
- Positive: the fix is structural (a URL shape), so it needs no maintenance when a new
  invitation is issued and requires no allowlist of "known" tokens.
- Negative, accepted residual risk: this redaction only covers this application's own
  Sentry instrumentation. It does **not** close the token's exposure in **hosting, CDN, or
  reverse-proxy access logs** (e.g. Vercel's own request logs, or any log aggregation a
  future deployment adds in front of this app) - those systems see the raw request line
  before this application's code ever runs, and are outside `src/platform/observability`'s
  reach entirely. A project that needs to close that gap too would need either a
  log-scrubbing policy at the hosting/CDN layer, or a redesign of decisions/0014's URL
  shape (e.g. resolving the token via a one-time redirect that exchanges it for a
  short-lived session before ever appearing in a log-bearing URL) - out of scope for this
  decision, which only closes the applicaton-level (Sentry) leak.
- Neutral: `sentryInitOptions`'s return type gained two function fields; any test asserting
  its exact shape (`src/platform/observability/tests/init-options.test.ts`) needed updating
  to expect them (`expect.any(Function)`) rather than an exact literal object.
- Implementation status: **implemented**. `src/platform/observability/core/init-options.ts`'s
  `redactInviteTokenFromUrl`/`beforeSend`/`beforeBreadcrumb`, with unit test coverage.

## Supersedes / Superseded By
- None. Builds on decisions/0014-workspaces-and-access.md's URL design without changing it.
